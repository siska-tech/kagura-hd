# VECTOR 最終画面マスク方式の試作

## 実装

全立体の線分をRAMの608x192/4bppマスクへpainter順で描き、その最終画面から同色の横runを抽出し、下方向に同じ色が続く範囲へ伸ばしてFILLする。既存のpage別背景消去は維持。トンネル後半のロゴはマスク描画後に既存BLITで重ねる。GPUへのマスク全面uploadは行わない。

単一1bppでは元の立体ごとの色と重なり順を表せないため、まず4bppで画素等価な対照実験を作った。maskは58,368B。静的workspaceであり、このengineは非再入・単一instance利用が前提。

## 結果

VECTOR20秒、33ms刻み607frame、同じseedで直前改善版と比較：

|項目|線分直接描画|最終mask→矩形|
|---|---:|---:|
|GPU commands（scene初期処理込み）|298,131|277,987|
|Host transactions|2,683,307|2,502,011|
|wire bytes|14,310,672|13,343,760|
|PC CPU総時間ms（単発観測）|34.43|92.92|

両page全byteは607frame全て一致。150秒4,546時刻の元版比較でも両pageとpaletteが一致。命令は6.76%減、CPU処理は増える。PC CPU時間はRP2040時間の予測ではない。実機未投入、30fps達成の根拠にはならない。

RP2040ビルドPASS。text315572B、bss247020B、stack設定8192B。リンクは通るがRAM余裕が小さい。実機評価前に147200Bのframeログを圧縮・集計化し、stack high-waterを測定する必要がある。この候補をそのまま性能版として採用しない。現在の実機Flashは前回改善版のまま。

## 判断

最終画面を先に作る構造は実現できた。しかし元の5x2ドットが離れた点線を形成するため、maskに統合しても矩形数が十分減らない。さらに重なりで違う色が細分化すると矩形が増える場合もある。貪欲矩形分割は最小矩形数を保証しない。

次の有力案は**低解像度の連続線mask**。例えば152x48の1bppは912B、3色の独立planeでも2736B。GPUへのFILL座標を4倍にする。線を点列で置く処理からmask上の連続線rasterizeへ変更し、重なり優先順位を合成時に適用する。3planeはcube/octasの3色には使えるが、6色トンネルには6planeまたはindexed maskが必要。152x48/4bppなら3648Bで全色を扱える。

ただしこれは元画素と一致しない。4px単位の階段や太さが変わるため、2x2／4x4相当の候補を並べて見た目と矩形数を評価する。各候補で完成maskを独立oracleとし、FILL列がそのmaskと一致するか検証する。物体数・回転・時間同期を維持し、輪郭の連続性を優先する。

改善幅をさらに狙うならpage別の前回最終maskとの差分だけを矩形化する。旧線消去も色0の変更領域として合成できる。近接矩形の過剰塗りは他色を壊すため、最終maskを参照して安全な範囲だけ許す。CPU生成・矩形化・Host投入・PRESENTを別計測し、30fps予算内か判定する。
