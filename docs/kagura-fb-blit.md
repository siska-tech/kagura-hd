# BLIT仕様・評価・実装

> 描画・カーソルのAPI契約はABI 1.4へ継承しています。本文の資源・STA・検証計画は開発時点の記録で、現行のPCM2構成・実機結果は [README](../README.md) を参照してください。


2026-11-04。**次の描画機能は、不透明な4bpp矩形コピー（COPY_RECT）を優先する。**
FILLとハードウェアカーソルを維持し、GLYPHと公開音源制御APIより先に検証する。
段階AのRTLとC／MicroPython APIをABI 1.2として実装した。opcode=6、能力bit6。
以下は設計判断と拡張段階を記し、末尾に実装の検証状況をまとめる。

## 用途と最初の範囲

優先用途は端末・一覧の縦スクロール、背面ページへの矩形複製、8画素単位の
ウィンドウ移動。同じ16色indexをそのまま複写し、全indexを不透明色として扱う。
カーソルは走査時合成なのでコピー元に含まれず、移動跡の保存・復元も不要。

| 段階 | 対応範囲 | 追加処理と判断 |
|---|---|---|
| A：現在の初期実装 | src/dstはページ0/1。X・幅は偶数、`src_x % 8 == dst_x % 8`。Y・高さは1画素単位。ページ内の重なり対応 | 同じword内byte位置を保ち、既存64 B転送窓を再利用。縦スクロールを先に成立させる |
| B：次の拡張 | 偶数X・偶数幅で送受Xの差が任意 | 0～3 byteの位置合わせが必要。狭い逐次処理と並列並べ替えを配置配線・速度で比較 |
| C：用途を見て選択 | 奇数X・奇数幅、色キー透過、常駐画像領域からの転送 | nibble位置合わせ、境界RMW、透過mask生成や画像の所有権を追加 |

Aでは「Xが8の倍数」や「幅が8の倍数」は必須ではない。例えばsrc_x=6、dst_x=14、
幅=202も対応する。src_x=0からdst_x=2への移動はB。奇数画素や透過が必要な矩形を
黙って丸めてコピーしない。SDKは未対応を明示し、アプリはGUIモデルから再描画する。C／Pythonのcopy_rectは自動クリップせず、ページ内の座標・整列を検証する。
α合成、拡大縮小、回転、任意ROPは初期BLITに含めない。

## 資源を増やしすぎないデータ経路

現行SPI構成はCLS 4,164/4,320（残156）、QSPIは4,126/4,320（残194）。
BSRAMは3/26だが、FFと接続の収容が厳しく、RAM残量だけでは追加可能と判断できない。
これはカーソル時点の比較用資源値である。既存の54 MHz、74.25 MHz、371.25 MHzを維持する。

`kagura_fb_registers.upload_data`の512 bitは、GPU実行中にCPUから書けず、
READ応答を一括取り込む経路を既に持つ。Aではこの64 BをBLITの作業領域として借りる。

1. 送受座標・サイズ・ページをすべて検証し、走査方向を決める。
2. 1行を最大16 wordの断片に分け、コピー元をword境界から読む。
3. 成功応答を既存`cmd_read_result`経路で転送窓へ取り込む。
4. 取り込みが終わってから転送窓をコピー先へmasked writeする。
5. 書込み成功後にだけ座標を進め、全行終了でtag付き完了を返す。

段階Aでは追加の512 bit作業バッファ、512 bit barrel shifter、乗算器、PLLは要求しない。
実装では既存転送窓の保持先を512 FFから16個の32bit SP BSRAMへ置換した。
各SPのword0を使い、CPUのbyte書込みにはSPのbyte enableを使う。
追加されるのは矩形・方向カウンタ、アドレス生成、byte mask、FSMと既存信号の選択経路。
この増分が残りCLSに入るかは未測定であり、必要ならFILLとの行走査・mask生成の共有を
試す。無条件に共通化すると制御fanoutと遅延が増えるため、合成値だけで採用しない。

**応答保持契約。** 現行READと同じく、GPUが`host_done`を認識した次のedgeで
レジスタ側がデータを取り込む。コントローラ／仲裁器の応答保持期間内であることを
結合試験でassertする。書込み要求は転送窓の更新後に発行する。CPUからの転送窓は
引き続きロックするが、GPU内部更新を許すため「upload_dataは完了まで不変」という旧契約を変更した。
SP書込み中は出力を保持し、次のread edgeで更新する。COPYのwrite受理はその後である。
通常READは窓が更新されるまで完了を1 edge遅らせる。CPUのbyte書込み後にも受付待ちを
1 edge入れ、直後の読出しが古い値を参照するのを防ぐ。完了後の転送窓内容は未定義とする。

メモリコントローラの`rdata`をそのまま書込入力にする案は採らない。コピー元読出しと
コピー先書込みの間に走査・PCMが入り、応答が置き換わるためである。転送窓なら保存でき、
読出し・書込みを一組として仲裁器をロックする必要もない。各transaction後に仲裁を戻す。

### 境界と重なり

4bppは偶数Xが上位nibble、stride=320 B、page base=0/115,200 B。
Aではsrc/dstのword内byte位置が一致するため、受信word列の並べ替えは不要。
先頭・末尾の不要byteは既存RWDS mask（1で書込み抑止）で保護し、宛先RMWは不要。
読み取る余分なbyteも行内に収まる。320 B strideと両page baseは4 B境界に揃っている。

- 同一ページで下方へ移すときは下の行から処理する。
- 同一ページ・同一Yで右方へ移すときは右の断片から処理する。
- それ以外は上から／左から。各断片を全部読んで保存してから書く。
- 同一ページ・同一座標は成功no-op。幅0または高さ0も、全入力検証後に成功no-op。
- 符号なし16 bit入力の加算は桁を拡張して検証し、切詰めによる範囲判定をしない。
  src/dstのX<640、Y<360、両矩形の右端<=640・下端<=360を要求する。

右向きの場合、現在の右端をE（exclusive byte address）とすると、断片の有効byte数は
`min(残り, 61 + ((E - 1) & 3))`。左向きは現在位置Pから
`min(残り, 64 - (P & 3))`。必要word数は`ceil((先頭byte位置 + 有効byte数)/4)`。
これで最大64 Bの受信窓からはみ出さず、左右どちらの重なりも保存される。

## 命令とSDK

既存の16 B記述子と1 outstanding/tag完了を維持する。新規FIFOやバッチ実行器は不要。
opcode6とcapability bit6はABI 1.2で実装した。

| byte | COPY_RECT |
|---|---|
| 0 | opcode=6 |
| 1 | bit0=src_page、bit1=dst_page、他0 |
| 2..3 | tag、little endian |
| 4..5 / 6..7 | src_x / src_y、uint16 little endian |
| 8..9 / 10..11 | dst_x / dst_y、uint16 little endian |
| 12..13 / 14..15 | width / height、uint16 little endian |

ABI minor=2、capability bit6は段階A専用のAligned Copy。
将来Bへ拡張するときもAの制約が消えたことを別途検出できるようにする。
既存のtag、BUSY、完了IRQ、FENCE、エラー4（メモリ失敗）を使う。
ページ外・範囲外はエラー3、予約bitや未対応の整列条件はエラー2で、最初のPSRAM要求前に拒否。
メモリ失敗やタイムアウト後の部分更新はロールバックされず、SDKは自動再試行しない。
背面ページをGUIモデルから再生成して復旧する。

Cでは`kfb_copy_rect(dev, src_page, sx, sy, dst_page, dx, dy, w, h)`、
MicroPythonでは同等の`copy_rect(...)`を提供する。両者とも同期ラッパーと
既存`submit/wait`による非同期利用を提供する。CPUがクリップする場合、送受座標を
同じ量だけずらして対応関係を保つ。整列制約を満たさなくなれば再描画へ戻す。
BLIT中も別CSRのカーソル更新は進める。

PRESENTはBLIT完了後に順序付ける。二重バッファの差分再生では、相対スクロールを
同じページへ二重実行しないようページ世代と完了tagを管理する。表示中ページへの書込みは
tear-freeを保証しない。BLITはページ間コピーにも使えるが、毎フレーム全面複写が必須になる
設計にはせず、dirty矩形と差分再生を比較する。

## 転送周期と帯域

既存RTLの`kagura_fb_arbiter`と`kagura_fb_burst_ctrl`を単独Verilator試験で接続し、
常時要求時の受理から次回受理までを1～16 word、read/write双方について測定した。
96区間でread=`27+2N`、write=`21+2N` sys cycleを確認した（LAT14、RDL6、CS-high2）。
64 Bのread+writeなら112 cycleで、コピーの有効データだけを数えた上限は約30.86 MB/s。
これはGPU内部の待ち、表示・PCMとの競合、ホスト通信を含まない。

| 操作・1ページ分 | コピー断片 | read+writeのバス上byte数 | transaction処理のみの時間 @54 MHz |
|---|---:|---:|---:|
| 全面640×360を別ページへ | 1,800 | 230,400 B | 3.733 ms |
| 16行上スクロール、COPY部分640×344 | 1,720 | 220,160 B | 3.567 ms |
| 上記＋下端16行FILL | COPY 1,720＋FILL 80 | 225,280 B | 3.646 ms |
| 200×100を右8画素へ | 200 | 20,000 B | 0.363 ms |
| 200×100、src/dstともword内byte位置3 | 200 | 20,800 B | 0.370 ms |

**この時間はGPU完了時間や実機fpsではない。** 内部FSMのbubbleを加えると増え、
走査・PCMの要求待ちや高優先度処理でさらに増える。命令送信も別途必要。
スクロールはCOPY+FILLで記述子32 Bとなり、CPUから115,200 Bを再送する方式に比べ
通信量を減らせるが、CPU実働時間の削減率はRP2040/RP2350で未測定。

毎秒60回スクロールする仮定で、走査の5 read/行・360行・60 fpsと、
2ch×48 kHz・8bit PCMがすべて1 word cache missとなる保守的なtransaction数を足すと、
処理周期の合計は54 MHzの**38.831%（1ページ更新）／60.707%（両ページへ差分再生）**。
走査6,372,000 cycle/s、PCM 2,784,000 cycle/s、COPY+FILL 196,880 cycle/回。
PCMの実miss率はアドレスとキャッシュ・先読みで変わる。書込み後のキャッシュ無効化もある。
この総量では帯域不足を理由に640×360・4bppを変更する必要性はまだ見えないが、
平均使用率は行期限の保証にならない。実行FSM込みの競合試験が採用条件となる。

## 実施済み検証と次の採用ゲート

再現コマンド：

```sh
python3 tools/analyze-fb-blit.py --output build/fb-blit-analysis.json
KAGURA_TEST_FILTER=tb_fb_burst_service bash tools/test-fb-verilator.sh
```

Pythonのtransaction計画モデルは、不変のコピー元から1画素ずつ生成する独立参照画像と
**884ケース**で両ページ全体を照合した。全byte位相、64 B付近の幅、左右上下・斜めの重なり、
ページ間、全面、端、空・同位置を含む。別の8ケースで未対応整列・範囲・ページを拒否。
これはアルゴリズムの検証であり、BLIT RTL実装を検証したものではない。RTLの検証結果は末尾を参照。

段階Aの採用ゲートは以下のとおり。

1. 転送窓再利用とread結果保持を結合し、他クライアントがread/write間に入る条件でも
   コピー元が壊れず、範囲外・未対応入力でメモリ要求が0であること。
2. ランダム矩形と四方向の重なりを同じ画素参照と照合する。エラー・reset後の完了tagと
   BUSY解除、カーソル独立更新、後続PRESENTを検証する。
3. 最大コピー＋走査＋6ch音源＋2ch PCMで、行取得<=1,920 sys cycle、音声異常0、
   画像・PCM一致を確認し、BLIT完了時間と仲裁待ちを別々に計測する。
4. SPI/QSPI双方を配置配線し、CLS/LUT/FF/BSRAM増分とSTAを記録する。
   現行のsetup>=+0.10 ns・setup/hold違反0を維持する。
5. Aの結果をもとにBのbyte位置合わせを評価する。Aが収まらなければ広いレジスタや
   payload選択経路の削減を先に行い、機能を追加したまま負のslackで採用しない。

実機のPSRAM外部I/O、USB/JTAG、RP側CPU負荷の評価は引き続き未完了。


## RTL・SDK実装の検証（2026-11-04）

矩形処理は`kagura_fb_fill_burst`を拡張し、FILLとCOPYで行走査・maskを共有した。
COPYの上下・左右方向、初期Yの乗算、source/destination間のword差、逆方向断片の
計算を段に分けた。命令モードとmemory request validを登録し、長いdecode経路を避ける。
命令層が全幅の範囲・空判定を先に行い、内部エンジンは検証済み・非空入力として動く。
独立FILL試験では従来の検証・空領域対応を維持する。

転送窓は`kagura_fb_upload_word`のSPを16個使う。小容量arrayの推論はGowinでFF化されたため、
実デバイスでは明示的にSPを使う。SP 32bitモードのAD[3:0]はbyte write enable、
AD[13:5]はword addressである。通常のVerilatorモデルに加えて、インストール済み
Gowin 1.9.11.03のSPモデルでも同じレジスタ試験を実施した。ローカル再現用は
`bash tools/test-fb-upload-gowin.sh`。ベンダーモデル自体はリポジトリへ追加しない。

起動診断は両FBページを黒、PCM領域240000..240127を無音の0で初期化する方式にした。
6音源は診断設定で動作し、2ch PCMの再生回路・HDMI音声も残る。初期化データをホストの
reset済み転送窓から供給し、起動専用パターンと512bit合流回路を除いた。
変化する画像・PCMデータはシミュレーション側から供給して照合する。

- `tb_fb_blit`：1,150ケース。独立した画素参照画像と両ページを全byte照合。
  全byte位相・64 B付近の幅・上下左右/斜めの重なり・ページ間・境界・空/同位置・
  範囲/整列不正・メモリ失敗・実行中resetと復旧を含む。
- `tb_fb_register_window`：最短間隔のbyte書込み/読戻し、6回のREAD完了順序、
  18回のCOPY途中capture、warm reset。通常モデルとベンダーSPモデルで通過。
- C/Pythonドライバは15試験が通過。重なり・ページ間、記述子一致、範囲/整列拒否、
  未対応firmware、メモリ失敗、投入応答喪失時の再送なしを確認。
- MicroPython 1.26 Unixでも重なり・部分word・ページ間・整列拒否が通過。
- SPI/QSPIの実プロトコルからCSR・転送窓・COPY・PSRAMまでの結合試験で全面一致。
  コピー中も走査・6音源・PCM 2ch・カーソルcommitを進め、行期限とPCM順序を検査する。

実機のPSRAM位相・外部I/O、RP2040/RP2350の実働時間、p95表示反映は未評価。
SPI/QSPIの配置配線結果と最終回帰は[実装記録](kagura-fb-implementation.md)に記録する。


最終確認：RTL全26試験、C/Python15試験、実MicroPython Unix、Gowin SPモデル試験が通過。
全面COPYは単独210,609 sys cycle（3.900 ms）、走査・6音源・PCM 2chとの結合時は
SPI252,756／QSPI252,696 sys cycle（約4.68 ms）。行取得は最大595／594 sys cycleで、
上限1,920以内だった。SPI／QSPIの数値STAもsetup +1.122／+0.660 ns、
hold +0.558／+0.552 ns、違反0で通過。Logic7,815／7,795、FF5,221／5,222、
CLS4,245／4,223（上限4,320）、BSRAM19/26、DSP1/10。640×360・4bppを維持する。
詳細なハッシュと試験条件は[実装記録](kagura-fb-implementation.md)を参照。
